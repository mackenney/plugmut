# Mutation Source Tracking

## Context

The `Mutation` dataclass in `mutmut/src/mutmut/file_mutation.py` (lines 25-29) has four fields:

```python
@dataclass(frozen=True)
class Mutation:
    original_node: cst.CSTNode
    mutated_node: cst.CSTNode
    context: Context
    annotation: str
```

There is no `source` field. When mutations are generated by plugins (e.g., `mutmut-extras` operators), there is no way to determine which operator or plugin created each mutant. The `.meta` files (written by `update_metadata()` in `file_mutation.py`) only store exit codes keyed by mutant name — no attribution data.

During e2e testing of `mutmut-extras`, identifying which mutations came from plugin operators vs builtins required manually inspecting diffs. This is unsustainable as more plugins and operators are added.

## Why It Matters

- **Plugin authors** cannot verify their operators are generating mutations without manual diff inspection.
- **Users** cannot determine which source (builtin vs plugin) produced surviving mutants — critical for evaluating whether adding a plugin improved test quality.
- **Reporting tools** cannot attribute results by operator or plugin, making comparative analysis impossible.
- **Debugging** mutation generation failures requires tracing through the full pipeline manually.

## Benefits

- Per-operator kill/survival reporting (e.g., "plugin operator `operator_augmented_assignment_swap` has 80% kill rate").
- Plugin debugging: confirm operators are firing on expected nodes.
- Comparative analysis: builtin vs plugin kill rates, operator effectiveness ranking.
- Foundation for future features like operator-specific configuration and selective mutation.

## Implementation Recommendation

### 1. Add `source` field to `Mutation` dataclass

In `mutmut/src/mutmut/file_mutation.py`:

```python
@dataclass(frozen=True)
class Mutation:
    original_node: cst.CSTNode
    mutated_node: cst.CSTNode
    context: Context
    annotation: str
    source: str = "builtin"
```

### 2. Propagate source from operators

In `MutationVisitor._create_mutations()` (file_mutation.py), when iterating over operators returned by `get_operators()`:

```python
source = getattr(operator_func, "__mutmut_source__", "builtin")
# Pass source when creating Mutation instances
```

Plugin operators in `mutmut-extras` would set this attribute:

```python
def operator_augmented_assignment_swap(node, **kwargs):
    ...

operator_augmented_assignment_swap.__mutmut_source__ = "mutmut-extras"
```

### 3. Thread source through the pipeline

- `combine_mutations_to_source()` (line ~230) aggregates mutations into `MutationsByLine`. The source needs to survive this grouping.
- `function_trampoline_arrangement()` (line ~266) creates the trampoline functions. The mutant name or metadata should encode or carry the source.
- `update_metadata()` should write source alongside exit codes in `.meta` files.

### 4. Metadata file format change

Current `.meta` format stores `{mutant_key: exit_code}`. Extend to:

```json
{
  "mutant__module__func__1": {"exit_code": 0, "source": "builtin"},
  "mutant__module__func__2": {"exit_code": 1, "source": "mutmut-extras"}
}
```

This is a breaking change to `.meta` format — add a version field or migration path.

### 5. Reference

The reference implementation at `~/pr/mutmut/` already has this pattern working end-to-end.
