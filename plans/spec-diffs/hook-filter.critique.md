# Adversarial Critique: Hook Filter Composition Spec Delta

## Verdict (up front)

The draft is a good start but contains critical structural problems that prevent it from serving as a behavioral contract: it conflates spec language with bug documentation, leaves the most important case (no plugins registered) unspecified, and uses undefined terms in its MUST statements. Several "open questions" are not questions at all — they're required contract decisions. The spec is not mergeable as-is.

---

## 1. Chaining Semantics Ambiguity

### 1a. "After None substitution" is undefined

The primary chaining MUST reads:

> plugin K+1 MUST receive the list returned by plugin K (after None substitution), not the list originally passed to the hook call site.

"After None substitution" is doing all the work and is never defined. A reader sees this and does not know what the substituted value is, or where it comes from.

The spec never introduces the concept of an **accumulator** — the running list that plugins transform sequentially. Without defining it, the MUST statements float free. Required addition:

> The caller MUST maintain an accumulator initialized to the mutations list provided at the call site. After each plugin call: if the plugin returned a non-None value, the accumulator MUST be replaced with that return value; if the plugin returned None, the accumulator MUST remain unchanged. At the end of the chain, the accumulator is the final result.

Without this definition, "None substitution" is uninterpretable.

### 1b. Ordering section contradicts itself

The "Ordering Guarantee" section says:

> Plugins with no ordering hint execute next (in pluggy registration order, stable).

but the Open Questions section says:

> Same-precedence relative order among plugins is not guaranteed and SHOULD NOT be relied upon.

These two statements are contradictory. The implementation IS deterministic (FIFO via `get_hookimpls()`), and the spec is asserting that in one place and denying it in another. Pick one and make it a MUST. If FIFO is the contract, say it. If it's unspecified, remove "in pluggy registration order, stable" from the body text.

### 1c. Empty-list short-circuit behavior between plugins is underspecified

The spec says:

> MUST: The hook is called even when the incoming mutations list is empty.

The context makes it appear this applies only to the **initial** call (no mutations were generated by the operator). But what about mid-chain? If plugin A returns `[]`, does plugin B still execute? The spec is silent on whether an intermediate `[]` short-circuits subsequent plugins or continues calling them with an empty list. Both behaviors are defensible; neither is specified.

## 2. Empty Result Handling

The table:

| Plugin return value | Effect on next plugin |
|---|---|
| `None` | Receives same list as this plugin |
| `[]` | Receives empty list |
| `[m1, m2, ...]` | Receives this list |

This is clear for the "next plugin" case. But the spec doesn't address the **terminal** case: what does the **caller** receive when the last plugin returns `[]`? The prose says "The final mutation list is the output of the last plugin in the chain" — but the table says nothing about the terminal plugin. This needs to be made explicit:

> The final result MUST be the accumulator value after the last plugin has been called. If the last plugin returns `None`, the result MUST be the value passed to that plugin, not `None`.

The current spec leaves it ambiguous whether "the output of the last plugin" means the plugin's return value or the accumulator after applying None-substitution.

---

## 3. None / Error Return Handling

### 3a. Exception handling breaks the chain — state is unspecified

> If a plugin raises an exception, it MUST propagate to the caller uncaught. The pipeline MUST NOT swallow filter exceptions.

"Caller" here is ambiguous: does it mean the `file_mutation.py` call site, or does it mean the top-level mutation runner? More importantly: when plugin B raises after plugin A has already modified the accumulator, what is the observable state? Does the partially-filtered list escape? Is the exception visible at the top level with the accumulated state attached?

The spec needs to say: "When a plugin raises, the exception MUST propagate and the accumulator at that point MUST be discarded — the caller MUST treat the exception as if the entire filter chain failed." Otherwise implementations may legitimately return a partially-filtered list alongside the exception, or wrap the exception with partial state.

### 3b. Non-list non-None return not addressed

A plugin might return a generator, a tuple, or any other iterable. The spec says the three cases are `None`, `[]`, and `[m1, m2, ...]`. What is the contract when a plugin returns `(m1, m2)` (a tuple)? Or `iter([m1])`? Either the spec must say "MUST return `list` or `None`" and treating non-list returns as errors is required, or it must say "MUST accept any iterable and coerce to list." Both are defensible; neither is stated.

---

## 4. Execution Order Not Defined

The spec states `tryfirst > regular > trylast` ordering. But:

- The `get_hookimpls()` call returns plugins in insertion/registration order. The spec says "in pluggy registration order" in one place and "not guaranteed" in another (contradiction documented above).
- For **same-precedence** groups, the internal order is unspecified. This is fine to leave unspecified, but only if the spec commits to it explicitly rather than vacillating.
- The spec says "A single plugin MUST NOT declare both `tryfirst=True` and `trylast=True`." — correct, but what is the behavior if a plugin violates this? Error? Treated as `trylast`? Treated as `tryfirst`? The spec must say.

The three-tier ordering `(tryfirst, regular, trylast)` needs a MUST that covers all three tiers together, not two separate `tryfirst` and `trylast` MUSTs that require inference to combine.

## 5. Backward Compatibility Contract

### 5a. "BREAKING" labeling on compatible behavior

The compat section says:

> BREAKING: A single-plugin system where the plugin returns non-None observes **identical** behavior under both old and new semantics.

Labeling something "BREAKING" and then saying it's identical is contradictory and misleading. This is a **compatible** case, not a breaking one.

### 5b. "MAY ... MUST" is invalid RFC 2119 construction

> MAY: Existing plugins written for last-wins semantics that happen to return non-None MUST be reviewed...

`MAY` and `MUST` cannot qualify the same statement. This reads as "it is optional, AND it is mandatory." The sentence must be rewritten. The intent appears to be: "Existing plugins that return non-None in a multi-plugin deployment MUST be audited before deployment under the new semantics."

### 5c. No contract for upgrading existing single-plugin deployments

The backward compat section covers two-plugin systems (breaking) and single-plugin systems (compatible). It says nothing about the upgrade path: if you add a second plugin to a previously-single-plugin deployment, what do you have to do? This is the most common real-world transition and it's unaddressed.

---

## 6. Parameter Subsetting Contract

### 6a. Spec documents a bug instead of a contract

The "Arg Subsetting Contract" section is split between "What the spec SHOULD guarantee (correct behavior)" and "What the branch currently guarantees (incorrect)." A spec MUST NOT contain sections describing incorrect behavior — that belongs in a bug tracker or code review, not a spec. The spec should only contain the correct behavioral contract, with a single sentence noting that the current implementation does not yet satisfy it.

Having "correct behavior" and "incorrect behavior" side-by-side in the same spec section teaches readers the wrong behavior first, then contradicts it.

**Required restructuring:** State the MUST invariant (arg subsetting MUST be honored). In a separate "Implementation Note" or strike through the current-behavior section entirely, noting only "the current implementation violates this invariant — see C1 in wave2-review-findings.md."

### 6b. The contract itself is incomplete

The MUST says:

> A filter plugin that omits `mutations` is nonsensical (cannot filter without it) but MUST NOT crash the caller.

If a plugin omits `mutations`, it receives no mutation list and cannot filter. What does the caller do with its return value? If it returns `None`, the accumulator passes through. If it returns `[]`, all mutations are removed. A plugin that doesn't receive the list but returns `[]` would silently delete all mutations. The spec must say: "A plugin that omits `mutations` from its signature SHOULD return `None`." Or stronger: "The hookspec MUST declare `mutations` as a required parameter."

## 7. No-Plugin Registered Contract

**This case is entirely missing from the spec.**

What happens when zero plugins implement `mutmut_filter_mutations`? The chain has no entries. The spec only defines behavior for N≥2 (chaining) and implicitly for N=1 (single plugin). For N=0:

- Is the initial mutations list passed through unchanged? (Expected.)
- Does the hook call site even execute the loop? (Presumably yes, no-op.)
- Is the return value `None` or the original list?

The N=0 case is the **most common deployment** (no filter plugins installed). It must be specified:

> When no plugins implement `mutmut_filter_mutations`, the hook MUST return the original mutations list unchanged. No filtering occurs.

Without this, a caller cannot rely on getting its mutations back when no filters are installed.

## 8. Additional Issues

### 8a. "Wrapper hooks are an open question" is unacceptable

Open Question 1 asks whether wrapper hooks should be explicitly prohibited. This is not a question — it has a definitive answer given the implementation: the branch bypasses pluggy's calling machinery entirely, so `@hookimpl(wrapper=True)` silently does nothing. The spec must say either "MUST NOT use wrapper hooks" (prohibit) or fix the implementation to support them. Leaving it as an open question means the spec is permitting behavior that will silently corrupt in production.

### 8b. "hookspec not updated" is a contract gap, not an open question

Open Question 4 asks whether the hookspec attribute should be updated. This is a required contract decision. If the hookspec currently says `firstresult=False` (or is absent) but the implementation no longer uses pluggy's fan-out, the hookspec is making a false promise to plugin authors who read it. The spec must state: "The hookspec MUST accurately reflect the composition semantics" and resolve whether `firstresult` or any other pluggy attribute applies.

### 8c. Submodule pointer failure is a merge-blocker not covered by the spec

Bug B2 says two tests fail because commit `f644cda` is not locally available. This is a merge blocker that must be stated as a pre-merge requirement:

> **Pre-merge requirement:** The submodule pointer MUST be updated to apply the chaining patch atop the locally-patched commit (`0431bc7`), not to an upstream commit that lacks the local patches. The recorded pointer (`f644cda`) is unavailable locally and the implementation it refers to does not exist in the working tree.

This is not a spec invariant but it is a correctness prerequisite that should be in a "Pre-Merge Requirements" section.

### 8d. Spec uses "should" (lowercase) in MUST-level sentences

Two places use unformatted lowercase "should" where RFC 2119 keywords are required:

- "The spec SHOULD document this migration requirement" — is this SHOULD or MUST?  
- "SHOULD NOT be relied upon" for ordering — this is fine, but the inconsistency in whether ordering is FIFO (body text) or unspecified (open questions) makes the SHOULD moot.
