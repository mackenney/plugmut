# Plan: Exploratory Mutation Patterns (Lower Priority)

> **This is a lower-value endeavor than `plan-new-operators.md`.** The operators in that plan are validated, generalizable, and purely structural. The patterns below are either harder to implement correctly, produce many equivalent mutants, require semantic context, or appeared in too few functions to confirm generalizability. They are worth revisiting after the high-priority operators ship and we have more LLM corpus data.

## Candidates worth further exploration

### A. `statement_reorder` — Swap adjacent statements

**What:** Swap two adjacent statements in a block.

**Why interesting:** Most frequent cross-function pattern in the experiment (6 occurrences, 3 functions). Catches ordering bugs: state mutation before check, yield before advance, counter increment timing.

**Why deferred:**
- Naively swapping ALL adjacent pairs creates a combinatorial explosion of mostly-equivalent mutants
- Needs heuristics: only swap when at least one statement has a side effect
- Needs lightweight def-use analysis: can't swap `x = 1` with `y = x + 2`
- Equivalent mutant rate estimated >50% without filtering

**Next step:** Build a prototype and measure equivalent mutant rate on real codebases. If <30% equivalent, promote to implementation.

---

### B. `swap_dict_key_value` — `d[k] = v` → `d[v] = k`

**What:** Swap key and value in subscript assignment.

**Why interesting:** Common logical error in mapping construction.

**Why deferred:**
- Only appeared in 1 function (parse_config) in the experiment
- Crashes when value is not hashable (e.g., `d[k] = [1, 2, 3]` → `d[[1,2,3]] = k` → TypeError)
- Would need type filtering or accept runtime errors during mutation testing

**Next step:** Run on more codebases to see frequency. Consider restricting to cases where both key and value are `cst.Name` nodes.

---

### C. `drop_defensive_copy` — `dict(x)` → `x`, `list(x)` → `x`

**What:** Remove constructor-based copies of mutable inputs, creating aliasing bugs.

**Why interesting:** Real bug pattern — forgetting to copy a mutable argument.

**Why deferred:**
- Only 1 occurrence in the experiment
- Hard to distinguish defensive copies from type conversions: `list(generator)` is materialization, not copying
- `dict(pairs)` is construction from pairs, not copying
- Would need heuristic: only when arg is a `cst.Name` that matches a function parameter

**Next step:** Restrict to narrow pattern: `dict(param_name)` or `list(param_name)` where `param_name` appears in the function signature. Prototype and measure false positive rate.

---

### D. `keyword_bool_arg_negate` — `fn(last=True)` → `fn(last=False)`

**What:** Flip explicit boolean keyword arguments in function calls.

**Why interesting:** 4 occurrences in LRUCache. Catches boolean parameter bugs.

**Why deferred:**
- Overlaps with existing `operator_name` which already flips True↔False everywhere
- The existing operator would already catch `fn(last=True)` by flipping the `True` literal
- Only adds value if the existing operator somehow skips keyword arg values (needs verification)

**Next step:** Verify whether `operator_name` already covers `True`/`False` inside keyword args. If yes, this is redundant. If no, it's a quick add.

---

### E. `remove_chained_method_call` — `x.method()` → `x` in expression context

**What:** Remove a zero-arg method call, keeping just the receiver object.

**Why interesting:** Different from void_call_removal (which targets standalone statements). This targets method calls embedded in expressions: `return domain.lower()` → `return domain`.

**Why deferred:**
- Very broad — would fire on every no-arg method call in every expression
- Many would be equivalent or crash (`x.copy()` → `x` is often equivalent; `x.items()` → `x` changes type)
- Needs filtering: only useful for specific method names (`.lower()`, `.upper()`, `.strip()`, `.sorted()`, `.copy()`)

**Next step:** Implement as a curated list of safe-to-remove methods rather than a generic pattern. This overlaps with the `sorted_removal` pattern from Stryker/Arcmutate.

---

### F. `exception_chaining_suppression` — `raise e` → `raise e from None`

**What:** Add `from None` to suppress exception chaining context.

**Why interesting:** Changes observable traceback behavior. Real pattern in libraries that wrap exceptions.

**Why deferred:**
- Only affects traceback display, not exception type or message
- Tests that only check exception type/message won't detect it
- Very niche — only matters for code that inspects `__cause__` or `__context__`

**Next step:** Low priority. Revisit if we add traceback-aware mutation testing.

---

### G. Patterns from literature not yet validated by LLM experiment

These appeared in the taxonomy but weren't generated by the LLM. Worth running targeted experiments:

| Pattern | Source | Notes |
|---------|--------|-------|
| `decorator_deletion` | MutPy, Cosmic-Ray | `@cache def f():` → `def f():`. High value but mutmut skips decorated functions entirely (by design, to avoid side effects). Would need to relax that filter. |
| `zero_iteration_loop` | MutPy, Cosmic-Ray | `for x in items:` → `for x in []:`. Straightforward but high equivalent mutant rate for loops that build results. |
| `one_iteration_loop` | MutPy | `for x in items:` → `for x in items[:1]:`. More nuanced than zero iteration. |
| `conditional_to_true_false` | PIT, Stryker | `if cond:` → `if True:` / `if False:`. Broadly useful but generates many mutations. |
| `regex_mutation` | Stryker weapon-regex | Mutate regex patterns. Complex to implement but high value for code with regexes. |
| `variable_replacement` | Cosmic-Ray | Replace a variable with another in-scope variable. Requires scope analysis. |

**Next step:** Run a second round of the LLM experiment specifically prompting for these patterns to gauge their usefulness and equivalent mutant rates.
